# Agent / System Architecture Preferences

- Prefers least-privilege tool access for AI agents: each agent gets only the tools it needs, since more tools increases hallucination risk. Confidence: 0.95
- Prefers explicit state-machine orchestration (Observe → Analyze → Plan → Safety → Act → Verify) over free-form model loops for complex agents. Confidence: 0.9
- Prefers verifying task completion against real observable state (e.g., screenshot goal-verifier) rather than trusting model output alone. Confidence: 0.9
- Prefers human-in-the-loop confirmation for risky or destructive actions (arbitrary shell commands, killing processes). Confidence: 0.9
- Prefers cross-session user preferences so the agent skips already-answered questions instead of re-asking. Confidence: 0.85
- Prefers persisting task/session state so work survives app restarts and crashes. Confidence: 0.8
- Prefers the agent to feel like a "skilled human assistant operating the computer" (See → Think → Speak → Act → Verify) with live commentary. Confidence: 0.8
- Prefers choosing the least invasive action that achieves the goal. Confidence: 0.75
- Prefers a clear layered separation of concerns: one Orchestrator (Main Agent Executor) deciding, specialist agents (Scratchpad, Clarification, Research, Planner) only advising, plus Infrastructure and Tools as separate layers. Confidence: 0.9
- Prefers specialist agents that only advise and never own the computer-control tools — the orchestrator always decides and acts. Confidence: 0.85
- Prefers reusing existing specialist subagents for the task types they were built for (e.g., the Strange Planner for visual suggestion/annotation tasks) rather than re-implementing equivalent logic inline in the main executor — when a subagent already exists, delegate to it. Confidence: 0.8
- Prefers a strict UI-automation-first action hierarchy: UIA control-pattern actions (invoke/set-value/select/toggle/expand/scroll-into-view) for native app controls, browser DOM (Playwright/CDP) for web-page controls (e.g., YouTube), and raw mouse_click with exact coordinates only as a last resort — never mouse clicks for web-page controls when the DOM is reachable. Confidence: 0.95
- Prefers identifying controls by stable AutomationId first, then Name + ControlType (returning bounds and enabled/visible state), and acting through the control's supported UIA pattern (Invoke, Value, SelectionItem, Toggle, ExpandCollapse, ScrollItem, Drag, DropTarget) rather than by model-guessed pixels. Confidence: 0.85
- Prefers calibrated physical drag-and-drop over a one-shot drag call: resolve source/target bounds via UIA, move to source center, mouseDown, interpolate 10–20 steps over ~300ms, brief pause over target, mouseUp, then verify the expected UI change — using UIA-returned bounds, not model-guessed pixels. Confidence: 0.8
- Prefers combined screen observation (screenshot + UI Automation + browser DOM + app state) rather than relying on screenshots/vision alone. Confidence: 0.85
- Prefers a lightweight always-on wake-word/VAD listener, with heavier AI components kept idle until activation. Confidence: 0.8
- Prefers non-blocking human-in-the-loop: the task suspends/resumes rather than blocking on a synchronous modal, and voice + on-screen options are answered in parallel with first-answer-wins. Confidence: 0.85
- Prefers registering every new tool/capability across all dispatch paths (model declaration, TS dispatcher, and Python direct-fallback map) so no fallback path silently fails. Confidence: 0.7
- Prefers keeping verification screenshots cheap — region-crop or downscale instead of sending full-screen PNG base64 per verification. Confidence: 0.7
- Prefers browser DOM element tools to return rich identifying attributes (id, name, type, placeholder, aria-label) in addition to text/bounds, so the model can pick the correct selector — and to accept name/placeholder fallbacks when a CSS id selector isn't stable (e.g., YouTube's search input is `name="search_query"`, not `id="search"`). Confidence: 0.8
- Prefers graceful fallback routing when swapping a subsystem — try the new path, fall back to the proven path on exception — over a hard cutover. Confidence: 0.6
- Prefers a dual-channel backend interface: REST endpoints for request/response commands and a single WebSocket for streaming/bidirectional events (tool execution, state changes, HITL, TTS). Confidence: 0.75
- Prefers typed, discriminated event messages — every WebSocket message carries a `type` field with a documented JSON payload schema rather than ad-hoc payloads. Confidence: 0.7
- Prefers a separate action budget for state-mutating tool calls; read-only observation calls (screenshots, window queries, UIA tree/text reads) do not count against the mutation budget. Confidence: 0.7
- Prefers re-observing (injecting a fresh screenshot) only after state-mutating actions, not after read-only observation calls, to avoid context bloat and slow turns. Confidence: 0.7
- Prefers system instructions that explicitly tell the model the system already supplies fresh screenshots after each action, so the model does not redundantly call observation tools and flail. Confidence: 0.65
- Prefers using human-in-the-loop for preference, browser/profile selection, and genuinely ambiguous choices — not just destructive/risky actions. Confidence: 0.9
- Prefers checking the current screen for already-open browsers/apps before launching a new instance, and asking the user for permission before reusing an existing window. Confidence: 0.8
- Prefers continuing an in-progress task from current context after a HITL answer — incorporate the answer and resume — rather than restarting from scratch. Confidence: 0.8
- Prefers verifying the correct search/input field is targeted before typing (e.g., browser address bar vs the Windows taskbar search box) so input lands in the intended control. Confidence: 0.75
- Prefers an explicit observe-first step at the start of every task: capture a screenshot plus the open-windows list, then decide the first action from real screen state rather than acting blind. Confidence: 0.85
- Prefers a short settle delay after a state-mutating action before capturing the post-action screenshot, so web-page animations/rendering finish and the verification frame is accurate. Confidence: 0.8
- Prefers scoping UI Automation searches to the currently focused window first (falling back to the desktop root) so a similarly-named element in another window isn't mis-targeted. Confidence: 0.8
- Prefers human-like cursor movement (cubic Bézier path with randomized control points, ease-out timing, slight jitter near the target, and a brief pre-click pause) over instant teleporting, so mouse actions feel natural. Confidence: 0.8
- Prefers telling the model the absolute screen origin of any cropped/region screenshot (and each open window's bounds) so mouse_click coordinates translate correctly from image-space to screen-space. Confidence: 0.7
- Prefers the agent to be decisive and switch strategy immediately rather than repeating the same failed action (e.g., clicking the wrong spot over and over). Confidence: 0.7
- Prefers the agent to be broadly capable beyond just computer execution — it should advise/plan (e.g., suggest a game move), delegate to subagents for reasoning, and annotate the screen (arrows/boxes) rather than declining such requests as "just an AI assistant". Confidence: 0.7
- For browser/DOM-driven tasks, prefers NO screenshots at all — the DOM tools (browser_get_url / browser_find_element / browser_list_elements) already see the page, so capturing a desktop screenshot after every browser_* call is redundant and drives up image cost; screenshots are reserved for native/desktop tasks. Confidence: 0.8
- Prefers a root agent at the very top of the hierarchy that knows every sub-agent's capabilities and dynamically routes/delegates tasks, invoking tools or sub-agents multiple times in a loop until the goal is reached — over a monolithic executor that does everything itself. Confidence: 0.9
- Prefers the executor to be a specialized sub-agent (one "professional in some task") alongside research, planner, etc., which the root composes (e.g., research → then executor for a PPT), rather than a single top-level agent that owns all logic. Confidence: 0.85
- Dislikes hardcoded task classification/routing (e.g., keyword-matching "suggest"/"recommend"/"next step" to pick a path) — routing must be dynamic/model-driven so novel and open-ended prompts still work. Confidence: 0.9
- Prefers sub-agents to be able to respond directly to the user OR hand results back to the root, which then routes to further sub-agents/tools for continued execution. Confidence: 0.75
- Makes the root/orchestrator the single entry point for all prompts — removes bypass routes (e.g., a per-request model override that skips the root) so every request flows through root routing; direct sub-agent execution is only a crash fallback. Confidence: 0.8
- The orchestration runner returns the most recent substantive text from ANY agent (root or sub-agent), so a sub-agent's final answer (research summary, executor outcome) reaches the user rather than only the root's echo. Confidence: 0.7
